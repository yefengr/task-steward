# 产品背景与术语

本文保存已经确认的产品背景与领域含义。具体系统设计、技术建议和待验证项见[首版技术方案](plans/active/20261112-initial-design.md)。当前仅有文档，所有能力均为待实现目标。

## 1. 使用者与问题

使用者是同时在多台电脑、多个项目中使用 Pi 的个人。任务通常来自已经明确的待办清单，也会在项目 Pi 会话中通过讨论逐步澄清。

需要解决三件事：

1. 不用逐台电脑、逐个会话检查，就能知道什么仍在执行、什么需要决策、什么已经交付。
2. 隔几天再验收时，能够直接理解原目标、已做工作、验证结果和验收方法，不依赖重新翻阅聊天。
3. 提前安排几项工作后，条件满足的任务能够继续执行，减少因用户没有及时下指令造成的空档。

目标是降低检查、回忆和安排工作的负担；持续占满机器并非独立目标。

## 2. 自建清单

清单本身是本项目的核心，不要求先在其他待办产品建立任务。首版不以外部待办集成为前提。

用户可以先只记一个标题，之后再补充说明、关联项目、设置顺序或与项目 Pi 讨论。任务不刻意区分讨论、调查或实现类型，同一任务可以在授权范围内自然推进这些工作。记录一项待办不等于授权立即执行；进入执行队列是明确的后续动作。

任务清单按项目组织。「需要我处理」是同一份任务数据的另一个视图，集中呈现待决策、待验收及执行异常，不建立第二套任务。

## 3. 角色与职责

| 角色 | 职责 | 项目上下文与模型 |
| --- | --- | --- |
| 用户 | 记录与安排任务，参与讨论，回答问题，确认交付或要求返修 | 确认目标与验收结果 |
| 控制台中心 | 保存清单、决定、依赖、执行与交付记录，派发任务，发送通知 | 不接入模型，不分析项目代码，不判断工作是否正确 |
| Mac worker | 管理本机项目映射、工作区和自身启动的 Pi，回传事件与结果 | 自身无需模型；负责启动项目 Pi |
| 项目 Pi | 在实际项目环境中讨论、调查、实现、验证、整理结论和交付 | 使用该 Mac 和项目的模型配置、认证、扩展、技能与规范 |
| Pi Reach | 提供具体 Pi 会话的对话、控制和时间线阅读入口 | 模型实际执行仍在对应 Mac |

不存在单独的中心「管家 Pi」。需要讨论时，由任务所属项目的 Pi 读取资料并参与讨论，用户通过 Pi Reach 直接交流。

## 4. 核心概念

| 概念 | 含义 |
| --- | --- |
| 项目 | 任务所属的工作范围，关联 Git 仓库与各 Mac 上的本地目录；同一项目可以登记在多台 Mac |
| 任务 | 用户希望完成的具体事项，持久保存目标、说明、决定、依赖和反馈，独立于进程生命周期；同一任务可包含讨论、调查、实现、验证与返修 |
| 执行队列 | 已明确安排开始的任务集合；清单排序与依赖关系分别表达优先级与前置条件 |
| 会话 | Pi 原生保存的对话记录。不同任务默认新开会话；同一任务可以关联多次运行，结束会话不删除原生历史 |
| 活跃受管会话 | 已取得本机名额、尚未由 worker 确认结束和释放的会话；正在工作、模型停稳或等待用户回应均占用名额 |
| 执行尝试 | 一次具体的运行，记录所用任务版本、机器、工作区、会话和结果；重试与返修保留历史 |
| 交付 | 项目 Pi 对本次工作提交的明确结果，包含结论、验证情况、验收方法和版本引用 |
| 需要回应 | 附在任务上的待处理事项；用户进入 Pi Reach 直接交流，任务保持进行中，会话继续占用名额 |
| 待验收 | 项目 Pi 已提交交付，等待用户或项目既有验收流程确认；不代表控制台已经判断正确 |
| 已暂停 | 用户主动结束会话且任务尚未交付；保留进展与工作现场，需用户选择继续后重新排队 |
| 已完成 | 用户或项目既有验收流程确认指定版本的交付通过 |
| 待核对 | 对执行进程或事件记录的当前情况缺乏可靠证据，需要恢复核对；不等同于失败或完成 |

讨论、调查等任务无需为了交付而修改代码。代码任务的交付应绑定 Git 提交；具体执行与版本规则见[技术方案](plans/active/20261112-initial-design.md#7-git-与项目流程)。

## 5. 主要使用路径

### 从待办到执行

用户创建并整理任务，明确项目和必要说明后加入队列。系统根据项目位置、用户选择、依赖及资源条件派发到对应 Mac，由项目 Pi 执行。

### 在任务中交流

任务由项目 Pi 推进，需要用户参与时通过管家通知，用户进入该任务对应的 Pi Reach 会话直接回答、追问或调整要求。问题不要求用户在管家页面另填回答、提交继续或重新入队，也不因等待回应就结束会话。

项目 Pi 把有意义的进展、重要决定与交付回传到任务。任务详情围绕目标与约定、当前进展、需要用户处理的事项、已有交付组织；Pi 的建议与用户已确认决定分别呈现，进展显示更新时间。仅打开 Pi Reach 不表示问题已解决。

### 从交付到验收

项目 Pi 提交交付说明，控制台保存并通过 PWA 通知用户。用户在任务详情阅读背景、结果、验证与操作步骤，确认指定版本通过；需要解释或修改时进入原任务的 Pi Reach 会话交流。返修保留旧交付与反馈，形成新版本后再次验收。

### 暂停与继续

Pi 明确交付并完成收尾后可以结束会话，用户也可以主动要求结束。会话结束与验收通过分别记录，原生会话历史保留。未交付时主动结束，任务进入已暂停；只有用户选择继续后才重新排队恢复，不自动再次启动。

### 自动续跑

自动续跑消费用户已安排的任务和明确依赖，不由中心模型生成下一步工作。每台 Mac 的最大活跃受管会话数可单独配置，默认 1；等待回应的会话也占用一个名额。worker 确认会话结束和释放后才归还名额，恢复历史会话同样需要取得名额。

前项等待验收时，独立任务在依赖、会话名额与验收积压限制允许的情况下仍可执行；确实需要前项确认的任务继续等待。具体规则见技术方案。

## 6. 首版边界

- 个人使用，自建清单，多台 Mac；首版不支持 Windows／Linux worker。服务器操作系统另按部署环境确定。
- 控制台部署在私人服务器，源码、Git 工作区和模型凭据留在执行 Mac。
- 对话复用 Pi Reach，不在控制台重新实现聊天时间线。
- 权限、提交、推送、合并及部署遵循各自项目规范和任务配置；管家不建立额外的工具审批体系。
- 代码使用 Git 管理，不建立中心源码备份包、自动搬迁代码或跨机器迁移运行中会话的系统。
- 中心根据明确操作、运行事件和项目 Pi 的结果报告更新状态，不以空闲、退出码或模型一句自然语言回复推断验收通过。
- 电脑离线时仍可读取服务器已有的任务与交付资料；访问源码、恢复会话及运行本机预览需要对应电脑在线。
- 首版不做多用户团队协作、电脑远程唤醒或外部待办同步。

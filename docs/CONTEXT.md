# 产品背景与术语

本文保存已经确认的产品背景与领域含义。具体系统设计、技术建议和待验证项见[首版技术方案](plans/active/20261112-initial-design.md)。当前仅有文档，所有能力均为待实现目标。

## 1. 使用者与问题

使用者是同时在多台电脑、多个项目中使用 Pi 和 Claude Code 等 Agent 的个人。当前面向私人自用，暂不公开提供服务。任务通常来自已经明确的待办清单，也会在项目的 Agent 会话中通过讨论逐步澄清。

需要解决三件事：

1. 不用逐台电脑、逐个会话检查，就能知道什么仍在执行、什么需要决策、什么已经交付。
2. 隔几天再验收时，能够直接理解原目标、已做工作、验证结果和验收方法，不依赖重新翻阅聊天。
3. 提前安排几项工作后，条件满足的任务能够自动开始，减少因用户没有及时下指令造成的空档。

目标是降低检查、回忆和安排工作的负担；持续占满机器并非独立目标。

## 2. 基本思路

本系统是一个任务台账，加上每台 Mac 上自动领取任务的启动器：平台安排任务、保存结果并提醒用户；启动器在无人值守时领取任务并启动 Agent；任务怎么完成，交给项目 Agent 和项目已有规范。Agent 已有的能力（重试、上下文压缩、会话保存，以及按项目规范调查、修改、验证、创建 worktree 和提交）直接复用，平台不重复建设。

执行任务的 Agent 支持 Pi 与 Claude Code 两种：Pi 经任务扩展接入，Claude Code 以技能为主接入，两者共用同一套平台与启动器；首版先接 Pi。创建任务时指定由哪种 Agent 执行。Agent 还可以在用户要求时代为查看、创建和修改任务，但不能安排开始或验收。

## 3. 自建清单

清单本身是本项目的核心，不要求先在其他待办产品建立任务。首版不以外部待办集成为前提。

用户可以先只记一个标题，之后再补充说明、关联项目、设置顺序或与项目 Agent 讨论；也可以在任意 Agent 会话中让它代为记录、查看或修改任务。任务不刻意区分讨论、调查或实现类型，同一任务可以在授权范围内自然推进这些工作。记录一项待办不等于授权立即执行；安排开始是明确的后续动作。

任务清单按项目组织。「需要我处理」是同一份任务数据的另一个视图，集中呈现待回应、待验收及已中断的任务，不建立第二套任务。

## 4. 角色与职责

| 角色 | 职责 | 项目上下文与模型 |
| --- | --- | --- |
| 用户 | 记录与安排任务，在对话入口与 Agent 交流，确认交付或要求返修 | 确认目标与验收结果 |
| 任务平台 | 保存清单、决定、依赖、执行与交付记录，判断哪些任务可以领取，发送通知 | 不接入模型，不托管 Agent 进程，不判断工作是否正确 |
| Mac 启动器 | 登记本机项目，按空闲名额自动领取任务，在后台 tmux 会话中启动 Agent，报告进程运行与退出 | 自身无需模型 |
| 项目 Agent | Pi 或 Claude Code。在实际项目中讨论、调查、实现、验证与返修，按项目规范处理 Git，回报进展、问题、决定与交付；用户要求时代为查看、创建和修改任务 | 使用该 Mac 和项目的模型配置、认证、扩展、技能与规范；Claude Code 经 ccx 在容器中运行 |
| 对话入口 | 与运行中的 Agent 对话：Pi 会话用 Pi Reach，Claude Code 会话用 Remote Control；也可在 Mac 终端接入 tmux 会话 | 模型实际执行仍在对应 Mac |

不存在单独的中心「管家 Agent」。需要讨论时，由任务所属项目的 Agent 参与，用户通过对话入口直接交流。

## 5. 核心概念

| 概念 | 含义 |
| --- | --- |
| 项目 | 任务所属的工作范围，关联 Git 仓库与各 Mac 上的本地目录；同一项目可以登记在多台 Mac |
| 任务 | 用户希望完成的具体事项，持久保存目标、说明、决定、依赖和反馈，独立于进程生命周期 |
| Agent | 执行任务的 Pi 或 Claude Code；创建任务时指定由哪种 Agent 执行 |
| 待领取 | 用户已安排开始、等待满足领取条件的任务；页面说明当前在等什么 |
| 领取 | 启动器为本机取得一项可领取任务；原子完成并带租约，同一任务不会被两处同时领取 |
| 名额 | 一台 Mac 同时运行的、由启动器启动的 Agent 进程上限，默认 1；进程运行（包括等待用户回应）即占用，退出即释放 |
| 会话 | Agent 原生保存的对话记录。每次领取新开会话，返修优先回到原会话；结束不删除原生历史 |
| 执行尝试 | 一次领取对应的一次执行，记录电脑、Agent 类型、会话、所用任务与依赖版本和结果 |
| 交付 | 项目 Agent 对本次工作提交的明确结果，包含结论、验证情况、验收方法和版本引用 |
| 需要回应 | Agent 提出、需要用户回答的事项；用户在对话入口原会话中交流，Agent 进程保持运行并继续占用名额 |
| 待验收 | 项目 Agent 已提交交付，等待用户确认；不代表平台已经判断正确 |
| 返修 | 用户对待验收交付要求修改或继续讨论；任务重新进入待领取并优先领取 |
| 已完成 | 用户确认指定版本的交付通过 |
| 已中断 | Agent 进程退出时没有交付；保留进展，由用户决定重新安排或取消 |
| 待核对 | 租约过期或电脑失联，缺乏可靠证据；不等同于失败或完成 |

讨论、调查等任务无需为了交付而修改代码。代码任务的交付应绑定 Git 提交；具体规则见[技术方案](plans/active/20261112-initial-design.md#7-git-与交付引用)。

## 6. 主要使用路径

### 从待办到执行

用户创建并整理任务，明确项目和必要说明后安排开始。项目所在 Mac 的启动器在有空闲名额且条件满足时自动领取，在后台 tmux 会话中启动新的 Agent 会话并带上任务背景。

### 在任务中交流

Agent 需要用户参与时提出问题，平台通知用户。任务页显示执行电脑、Agent 类型与会话标识，用户在对应的对话入口打开该会话直接回答、追问或调整要求；等待期间 Agent 保持运行。问题由 Agent 根据后续交流更新、解决或撤销，仅收到回复或打开会话不表示问题已解决。

Agent 把有意义的进展、重要决定与交付回报到任务。任务详情围绕目标与约定、当前进展、需要用户处理的事项、已有交付组织；Agent 的建议与用户已确认决定分别呈现。

### 从交付到验收

Agent 提交交付并收尾后结束进程，任务进入待验收，平台通知用户。用户在任务详情阅读背景、结果、验证与验收方法，确认指定版本通过；需要解释或修改时要求返修，任务优先重新领取，Agent 优先回到原会话继续，形成新的交付版本。旧版本的确认不能应用到新版本。

### 中断

Agent 进程退出时没有交付，任务进入已中断，不自动重开；用户选择重新安排或取消。电脑失联时任务显示待核对，不转给其他电脑。

### 自动续跑

启动器释放名额后继续领取下一项可领取任务。领取需同时满足：依赖已满足（默认等前项验收通过，也可选择前项交付后即可开始）、待验收数量未达上限（初始三项，返修不受限制）、电脑匹配。自动续跑只依据用户已安排的任务和显式依赖，不由模型猜测下一步工作。

Git 项目的任务默认使用独立分支和 worktree，不纳入原目录未提交的改动，由项目 Agent 按项目规范创建。后项领取时记录实际使用的前项交付版本；前项之后返修，只提示后项，不静默改变其基线。

## 7. 首版边界

- 个人使用，自建清单，多台 Mac；首版不支持 Windows／Linux 执行端。服务器操作系统另按部署环境确定。
- 平台在私人服务器以单 Docker 容器运行，利用已有 Docker Compose 与 HTTPS 环境。身份按个人使用简化，保留必要访问保护，不建设公开注册、团队权限或复杂设备审批体系。
- 执行任务的 Agent 为 Pi 与 Claude Code，首版先接 Pi；Claude Code 经 ccx 在容器中运行。
- 首版只由启动器领取任务；手工打开的 Agent 不领取任务、不计入名额，用户仍可独立使用。
- Agent 可代用户查看、创建和修改任务；安排开始与验收只能由用户在平台操作。
- 源码、Git 工作区、Agent 原生会话和模型凭据留在执行 Mac。
- 管家独立、轻量，对话通过各 Agent 的远程入口进行；不在管家内嵌会话页面，精确会话深链作为后续增强。通用 PWA 基础可按需要复用。
- 权限、提交、推送、合并及部署遵循各自项目规范和任务配置；管家不建立额外的工具审批体系。
- 平台根据用户操作、启动器报告的进程事实和项目 Agent 的明确回报更新状态，不以进程退出、退出码或模型一句自然语言回复推断验收通过。
- 电脑离线时仍可读取服务器已有的任务与交付资料；访问源码和运行本机预览需要对应电脑在线。
- 首版不做多用户团队协作、电脑远程唤醒或外部待办同步。

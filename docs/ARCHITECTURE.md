# 当前架构与模块边界

本文保存当前代码的结构与运行链路，承接已结束的首版方案中仍有效的架构事实。产品含义见 [CONTEXT](CONTEXT.md)，事项及验收状态只看 [ROADMAP](ROADMAP.md)，安装和运维操作见 [DEPLOYMENT](DEPLOYMENT.md)。合入仓库不代表已发布或已部署。

## 1. 系统边界

Task Steward 是任务台账与 Mac 启动器，不是中心 Agent。平台不接模型、不托管 Agent 进程，也不读取对话推断任务完成。模型、项目规范、源码、Git 工作区和 Pi 原生会话留在执行 Mac。

- 浏览器通过 HTTPS 访问同一个平台进程提供的 API 与静态网页。
- Mac 启动器主动向平台心跳、领取、续租和报告退出，无需开放 Mac 公网端口。
- 启动器在独立的 tmux server `steward` 中启动交互式 Pi。Pi 扩展直接向平台读取任务与回报。
- 对话仍在 Pi Reach 或本机终端完成。任务链路不替代 Pi Reach 的配对、Relay 和会话存储。
- 当前执行端只接 Pi。Claude Code、Web Push、依赖调度与验收积压门禁仍是 [BACKLOG](BACKLOG.md) 中的候选，不能从旧方案的完整产品设计推定已实现。

## 2. 模块及直接消费者

| 模块 | 当前职责 | 直接消费者或运行入口 |
| --- | --- | --- |
| `packages/contract` | Zod schema、任务状态、错误码、时间参数与本机配置；保持浏览器可用 | platform、web、launcher、platform-http、pi-extension |
| `apps/platform` | Hono API、访问认证、配对、任务管理、领取与租约、讨论控制、会话操作、SQLite 与静态前端 | 浏览器、launcher、Pi 扩展；`dist/index.js` 与 `dist/admin.js` |
| `apps/web` | React / Vite / Mantine 控制台；登录、项目、任务、电脑与配对页面，中英切换 | platform 托管构建产物；浏览器执行 |
| `packages/platform-http` | 平台 HTTP 传输；macOS 系统代理交给 Swift / URLSession，其他模式使用 Node | launcher、pi-extension；不是浏览器依赖 |
| `packages/execution-runtime` | 同机目标的 SQLite 事务锁和保守 PID 存活探测；不含平台状态或会话副本 | launcher、pi-extension；仅 Node，不进入浏览器契约 |
| `apps/launcher` | `stew` CLI、配对、项目登记、LaunchAgent、tmux 生命周期、本机状态与恢复、验收后的本地 Git 合并及清理 | Mac 用户、LaunchAgent；与扩展共同打入 npm 包 |
| `packages/pi-extension` | 普通 Pi 查建改、明确目标登记与动态执行绑定；Git 基线及现场核验、回报、讨论与收尾 | Pi 原生登记同一实际本地包；启动器仍显式加载同一入口 |

根 workspace、各包 `package.json` 和 contract 是接口及依赖真源，不在文档复制完整 schema。contract 先编译到 `dist`；platform-http 构建 macOS 原生辅助程序，故根 `typecheck`、`test` 也有构建前置。开发环境见 [README](../README.md#本地开发)。

## 3. 执行、交付与验收

1. 用户或普通 Pi 记录待办，不自动安排开始。当前任务类型为实现（默认）或讨论；安排、取消、验收及返修由用户在工作台操作。
2. 平台在事务中为合适的在线电脑领取任务，生成带租约的执行尝试。返修优先，且同一任务的旧尝试未结束时不能再次领取。电脑选路与等待原因由平台判断，不由模型猜测。
3. 启动器先保存请求标识和待启动状态，再创建精确的 tmux 目标。固定首条消息要求 Pi 读取完整任务；任务正文与反馈走 API，不拼入命令行。
4. Pi 按项目规则与本次授权工作，回报进展、问题、决定和交付。项目原有记录仍应按授权更新，Steward 不能成为第二套项目状态真源。
5. 已保存交付使任务进入待验收，用户只能验收最新交付版本。普通前台目标收尾后结算本目标执行，保留 Pi 以便开始其他目标；它不占后台名额。当前后台执行仍在确认 Pi 退出后结算和释放后台名额，等待用户回复仍占后台名额；统一后台交付生命周期由后续任务接入。
6. 无交付退出记为中断；取消、退出报告和用户验收分别处理，迟到报告不覆盖新状态。租约过期显示待核对，不凭断线重派任务。

任务主状态保持未安排、待领取、进行中、待验收、已完成、已中断、已取消。Git 生命周期用任务的附加阶段区分用户验收后的待合并、合并受阻、待清理及清理受阻；底层仍处于 `review`，但界面不再显示为等待用户验收，完成清理后才转为 `done`。需要回应与待核对也不是额外主状态。交付、验收、Git 合并、清理、npm 发布及平台上线是不同事实。

### 讨论与提醒

讨论不会因为回合结束、已经有结论或暂时没有回复而自动交付。用户在原 Pi 会话发送「结束讨论」，或在工作台点击「结束讨论」；平台确认结束请求后，Pi 才整理结论和未决事项、保存交付并收尾；普通前台 Pi 保持运行，当前任务台后台 Pi 仍按退出流程收尾。工作台请求可在执行电脑离线时保留，恢复连接后处理。

两种任务都只有在 Pi 用 `steward_ask` 提出明确问题并等待回复满三分钟后，才显示一次工作台提醒。原会话收到回复会撤下提醒，但不自动解决问题；打开会话不算回复，普通聊天不触发提醒，也不向平台同步聊天内容。

### 工作现场与会话恢复

Git 实现默认使用独立分支与工作树，保留原目录的未提交改动；只读任务不创建工作树。Pi 在实际目标会话登记目录、Git 分支和原生会话定位，迁移后重新确认。返修基于被返修交付的同机实际定位恢复；现场缺失或不匹配时停止并确认，不猜测其他会话或创建替代现场。

用户可手动重启仍在运行的 Pi，或恢复已退出的原会话；要求原 Mac 在线、启动器支持且精确目录与会话文件可用。普通重启／恢复不重放开工指令，返修则带入新反馈。重新安排是新执行，不等同于恢复原对话。历史事故与隔离回归范围见[会话恢复回归记录](plans/completed/20261124-session-locator-regression.md)。

### 前台纳管与后台接续

普通 Pi 的模型在开始明确工作目标时调用 `steward_begin_task`。目标使用原生会话自定义记录中的稳定 goalId，同目标多轮及重载沿用；普通问答不建任务。新目标直接登记为 running/foreground，不进入 queued。未配对、令牌失效或断网的新目标须明确尚未纳管，可按本地授权工作；已纳管历史恢复失败不能借此绕过执行所有权。

前台权限还要求当前机器认证、进程内 ownerId、本机目标锁和平台当前尝试校验。ownerId 不写入对话或公开任务视图；历史只提供定位线索，不能取得回报或交付权限。原生重载或工作树迁移重新绑定时，同一任务使用新的尝试封闭旧代权限，隔离迟到回报，并重读原生定位、核对实际现场；不复制对话到另一套系统。互斥同时检查原生会话的其他活跃任务和未结束交接，不能换目标编号绕过占用；独立目标应使用原生新会话或 fork。

用户点击「后台继续」后，复用 session_operations 的 stop → launch → loaded 流程。仅原电脑在线、启动器支持且有后台名额时接受；stop 阶段预留一个后台名额。启动器不会终止前台进程，必须确认原 PID 已消失、取得目标独占锁、核对会话和 Git 快照，才报告可交接。PID 仍活着、权限不足或状态未知均阻止启动；脏主目录保留原样，等待用户回原会话核对处理。平台在事务中封闭源尝试，再建立同任务的后台尝试，保留接续关系。

前台交付后的后台返修也经同一 stop/launch 链，而不从旧领取路径直接打开仍被普通 Pi 使用的对话。某任务缺确认现场时仅阻塞该任务，不挡住同机其他可执行待办。已确认同一 locator 的现场可随前台恢复继承；迁移后的定位不同则重新核对。

普通 Pi 交付结算不代表原进程已退出，也不能用 OS cwd 证明原生会话的逻辑工作树已无人使用。代码交付的验收操作保留源前台进程身份；程序无法确认其退出时暂停合并与清理，显示原因，不自动关闭普通 Pi 或删除可能仍在使用的工作树。用户退出原 Pi 后可重试，既有 Git 合并器和清理器不重建。

后台通过原生 `--session` 打开原对话。平台同时确认进程启动和原会话加载后，扩展复用控制轮询，在空闲时发送一次核对最新目标、授权、进展和中断操作结果的新接续消息，不重放初次开工指令。一次性发送意图保存在原生记录中，重载或发送结果未知不自动重放；用户先输入时不再追加自动接续。普通重启／恢复仍只打开原会话等待用户，不混用接续语义。任务 origin 与 executionMode 分别保存发起来源和执行方式；旧记录缺来源证据时显示历史来源未记录，不用 createdBy 猜测。

### 代码任务的基线、合并与清理

项目 Git 设置保存在平台，机器心跳登记目录不会覆盖用户配置。已有项目的默认基准分支保持未配置，需用户明确设置；任务可覆盖默认值。首次领取时冻结整个分支和同步选择，包括未配置的空值，不因项目设置变化而漂移。缺分支时只允许通过任务编辑显式补第一次选择，同时原子确认该时点的项目同步设置。扩展在代码写入前通过 `steward_prepare_git` 执行本地安全同步并保存快照，返回创建任务工作树所需的确切基线。无上游不是同步失败；失败不会隐式降级为不联网开工。讨论或只读任务不调用准备工具。

创建和会话迁移继续复用 Pi 原有工作树能力。扩展登记现场和提交交付时核验同一仓库、独立分支、工作树所有权、实际提交与现场状态。平台保存声明及定位，不托管源码，也不通过服务器读取 Mac 文件。

用户验收代码交付后，平台保存绑定电脑、交付版本和确切提交的操作。只有支持 Git 生命周期的启动器才能获取操作；旧尝试或会话操作未结束时不能合并或清理。启动器使用仓库级锁、原生 Git argv 和持久操作记录处理合并与重试，不执行模型生成的合并命令。实际分支推进使用明确 ref 和旧提交的原子比较更新，不向其他已检出基准分支的工作树执行 merge；目标已检出时安全暂停，避免外部维护者切分支造成误写。最终仅快进到已验收提交，目标已分叉则回到原现场返修并重新验收。

平台确认合并结果后才允许清理。启动器对任务专用 Pi 工作树的所有权、分支及占用重新检查，再用 Git 安全移除工作树和分支；不强制删除，不重建会话。公开 Pi 工作树包没有独立的启动器调用接口，因此这里使用最小原生 Git 适配，不另建工作树创建器或会话管理体系。合并结果与清理结果分阶段记录，断线或崩溃后不能把已合并任务当作未操作重做。旧的无 Git 快照交付保留原有验收行为，不补造历史基线和提交。

## 4. 数据、身份与故障边界

- 平台以 Node 内置 SQLite、SQL 迁移及 `PRAGMA user_version` 管理持久数据，文件库启用 WAL；数据库访问封装在 platform。迁移以 `apps/platform/migrations/` 为准，备份与回滚见部署文档，不凭旧表格手工改生产库。
- 浏览器使用密码登录和受保护 Cookie；写请求验证 Origin。启动器使用本机机器令牌；执行回报还绑定当前尝试，普通任务管理只使用机器令牌。令牌、密码与模型认证不进入仓库或提示词。
- 写请求用稳定请求标识做幂等回放；授权、归属和版本冲突仍须检查。请求结果未知时沿用原参数重试，不能当作从未写入。
- 启动器的本机状态、未确认事件与会话定位用于重启核对；tmux 查询失败不等于会话已经退出。已保存交付不因一次网络故障撤回。
- Mac 必须保持用户登录和可运行状态；不承诺休眠、退出登录时继续执行或自动唤醒。普通手工 Pi 不参与后台自动领取和名额统计，但可登记并执行当前明确目标；转后台必须经过显式接续与所有权交接。

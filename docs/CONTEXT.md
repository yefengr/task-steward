# 产品背景与术语

本文保存产品背景、领域含义与当前使用边界。模块和运行链路见 [ARCHITECTURE](ARCHITECTURE.md)，操作见 [DEPLOYMENT](DEPLOYMENT.md)，已确定事项及状态以[路线图](ROADMAP.md)为唯一权威来源；Steward 记录仅作辅助。[首版技术方案](plans/completed/20261112-initial-design.md)保留历史决策，不是当前能力清单。

## 1. 定位、使用者与问题

**定位**：Task Steward 是 Agent 工作的辅助调度台。方案写在项目里，任务在 Steward 里排好依赖；用户一句话开工，它在 Mac 上并行、按先后启动后台 Agent，让用户随时看清进度，做完帮用户收干净现场。它不替代项目自己的规范、文档和验收。

使用者是在多个项目中使用 Claude Code 和 Pi 的个人，当前私人自用，暂不公开提供服务。日常在 Claude Code 或 Pi 会话中讨论需求、制定方案和任务，方案按项目规则写进项目；定稿后希望任务不必逐个手动开工，而是提前安排好，在后台并行、按先后自动执行；验收由用户自己掌握。有的项目走 Pull Request，有的不走。

需要解决四件事：

1. **定稿就能开工**：在对话中明确说开始就能安排，不必再去网页逐个操作，也不因为没有及时下指令而空等。
2. **后台并行，按先后推进**：同一台 Mac 同时执行多个互不依赖的任务，各用独立的工作树和会话；有依赖的任务在前项满足条件后自动开始。
3. **随时看清进度**：哪些在执行、哪些在等我回答（并能直接打开那个会话）、哪些已经交付，一处可见；隔几天再看，交付记录也能说清原目标、已做工作、验证结果和验收方法，不依赖重新翻阅聊天。
4. **做完收干净**：合入确认后清理任务工作树和分支，不留残骸。

目标是让提前安排好的工作在无人值守时也能并行推进，同时降低检查、回忆和收尾的负担；把机器占满本身不是目标。

### 不做什么

- 不保存方案，也不是项目事项状态的来源；项目离开 Steward 也能照常开发。
- 不替代项目规范：怎么做、怎么记录、怎么提交、推送和合并，由项目规则和执行 Agent 决定。
- 不设验收门禁，不判断工作是否正确。
- 不提供问答界面，提问和回答都在会话中进行。
- 不接模型，不托管 Agent 进程。

## 2. 基本思路

讨论和执行分开：用户在 Agent 对话中想清楚做什么、先做什么，并把方案写进项目；Steward 负责什么时候开始、在哪台电脑上跑、做完怎么收尾；任务内部怎么完成，交给执行 Agent 和项目规范。

平台只记录事实、做判断：哪些任务可以开始、谁在执行、交付了什么、是否已经验收、收尾到了哪一步。涉及进程和 Git 的动作都在执行 Mac 上，由启动器按平台记录的决定执行。Agent 已有的能力（重试、上下文压缩、会话保存，以及按项目规范调查、修改、验证、创建 worktree 和提交）直接复用，平台不重复建设。评估新需求时先分清：这是跨任务的调度、记录或收尾问题，还是执行 Agent 自己能处理的项目执行问题；后者交给 Agent 和项目规范。

### 开工单与开工条件

Steward 的任务是一张开工单，不承载方案正文，包含：

- 一句话目标；
- 方案位置：项目中的文件和章节，开工前必须已在基准分支上；
- 依赖的任务；
- 授权范围：能做什么、不能做什么，完成后推进到哪一步（例如开 PR、合并、发布到测试环境），上限由项目规则决定；
- 所属项目和基准分支。

任务之间的先后关系用依赖表达，不另设「计划」对象。用户在对话中明确授权或在工作台安排后，只要方案已在基准分支、依赖已满足、有空闲名额，启动器就开工；没有依赖的任务同时开始。Steward 只检查方案文件是否存在，不代为提交。依赖以哪个节点为满足条件在设计依赖调度时确定；倾向前项合入后再开始后项，使后项从包含前项代码的基准开工，讨论类前项以验收为准。

### 从开工到收尾

1. 在 Claude Code 或 Pi 中讨论，定下方案，按项目规则提交进基准分支；走 PR 的项目先合并。
2. 讨论中的 Agent 起草开工单和依赖，用户确认后说开始。
3. Steward 检查开工条件，启动器在后台开工。
4. 执行中需要用户决定时，Agent 在会话中提问，Steward 提示是哪个会话在等。
5. 交付后由用户验收。
6. 合入：走 PR 的项目由执行 Agent 或用户按项目规则推分支、开 PR、合并，Steward 只记录；不走 PR 的项目按项目设置由启动器在本地快进合并，这是项目可选项。
7. 合入确认后，Steward 清理工作树和分支，依赖它的任务自动开始。

在对话中直接动手的工作，也可以通过前台登记纳入同一份台账。

### 定稿依据

定位于 2026-11-27 定稿，依据当时线上的使用记录（11-20 至 11-27）：后台执行能力不是瓶颈，两台 Mac 各配 5 个名额，从未占满；打断后台执行的主要来源是发布等外部操作（部分源于扩展提示词统一禁止 Agent 推送和合入）、Steward 自身的现场与生命周期机制，以及开工信息不全或方案未提交；返修多数用于推进下一步或继续讨论，而不是结果不满意。因此优先削减 Steward 自身造成的打断，再补依赖与整批开工。

## 3. 自建清单

清单本身是本项目的核心，不要求先在其他待办产品建立任务。首版不以外部待办集成为前提。

用户可以先只记一个标题，之后再补充说明、关联项目或与项目 Agent 讨论，也可在已配置扩展的普通 Pi 会话中让它代为记录、查看或修改任务。创建时区分「实现」（默认）与「讨论」：实现按目标执行和验证，讨论只围绕目标交流并由用户主动结束。调查可按授权包含在对应目标内，任务类型本身不扩大写入权限。记录待办不等于授权立即执行；安排开始是明确的后续动作。

任务清单按项目组织。规划中的「需要我处理」会集中呈现待回应、待验收及已中断的任务，是同一份数据的视图，不建立第二套任务；当前由项目列表和任务详情承载这些信息。

对已有项目，Steward 不取代项目既定的任务管理机制与记录。以本仓库为例，ROADMAP 维护已确定事项的状态，BACKLOG 收录候选；Agent 的平台回报不能替代项目要求的更新，相关写入仍须得到本次授权。

## 4. 角色与职责

| 角色 | 职责 | 项目上下文与模型 |
| --- | --- | --- |
| 用户 | 在对话中讨论并确认任务及先后关系，授权开始，与执行中的 Agent 交流，确认交付或要求返修 | 确认目标与验收结果 |
| 讨论入口 | Claude Code 或 Pi 会话：讨论需求，按项目规则写方案，起草开工单和依赖，用户明确要求时代为安排开始，查看进度 | 当前只有 Pi 能查看、创建和修改任务；Claude Code 入口与对话中安排开始尚未实现 |
| 任务平台 | 保存清单、决定、执行与交付记录，判断哪些任务可以领取，呈现工作台提醒；系统推送尚未接入 | 不接入模型，不托管 Agent 进程，不判断工作是否正确 |
| Mac 启动器 | 登记本机项目，按空闲名额自动领取任务，在后台 tmux 会话中启动 Agent，报告进程运行与退出 | 自身无需模型 |
| 项目 Agent | 当前为 Pi。在实际项目中按目标与授权讨论、调查、实现、验证和返修，遵循项目规范处理 Git 与项目记录，回报进展、问题、决定和交付 | 使用该 Mac 和项目的模型配置、认证、扩展、技能与规范；Claude Code 接入另议 |
| 对话入口 | 与执行中的 Agent 交流。当前 Pi 会话用 Pi Reach，也可在 Mac 终端接入 tmux；Claude Code 的 Remote Control 仍待接入验证 | 模型实际执行仍在对应 Mac |

不存在单独的中心「管家 Agent」。需要讨论时，由任务所属项目的 Agent 参与，用户通过对话入口直接交流。

## 5. 核心概念

| 概念 | 含义 |
| --- | --- |
| 项目 | 任务所属的工作范围，关联 Git 仓库与各 Mac 上的本地目录；项目设置默认基准分支和开工前同步选项 |
| 基准分支 | 任务分支的起点，也是该任务验收后的合并目标；任务可在开工前覆盖项目默认值 |
| 任务工作树 | 本任务专用的 Git linked worktree；任务运行目录通常就是该工作树或其中的子目录 |
| 任务 | 用户希望完成的具体事项，持久保存目标、说明、决定和反馈，独立于进程生命周期 |
| Agent | 当前执行任务的 Pi；模型与工具权限沿用执行 Mac 和项目配置，Claude Code 字段预留但尚不可执行 |
| 任务类型 | 实现或讨论，与 Agent 类型不同；讨论必须由用户主动请求结束 |
| 待领取 | 用户已安排开始、等待满足领取条件的任务；页面说明当前在等什么 |
| 领取 | 启动器为本机取得一项可领取任务；原子完成并带租约，同一任务不会被两处同时领取 |
| 名额 | 一台 Mac 的后台领取额度，默认 1；前台执行不占用。后台执行及接续中的保留槽占用额度，当前后台进程等待用户时仍占用 |
| 会话 | Agent 原生保存的对话记录。首次执行新开会话；返修核对并复用上次交付的同机实际现场，无法定位时暂停；结束不删除原生历史 |
| 执行尝试 | 一次已获授权的前台绑定或后台领取／接续，记录电脑、执行方式、实际会话与工作现场、执行时间和结果 |
| 交付 | 项目 Agent 对本次工作提交的明确结果，包含结论、验证情况、验收方法和版本引用 |
| 需要回应 | Agent 提出、需要用户回答的事项；用户在原会话交流。等待不是中断；前台不占后台名额，后台等待仍占用 |
| 待验收 | 项目 Agent 已提交交付，等待用户确认；不代表平台已经判断正确 |
| 返修 | 用户对未最终验收的交付正式要求修改；按后台资格接续原现场，形成新交付后重新确认 |
| 已完成 | 已最终验收并完成适用的退出和清理；代码须先安全合并，讨论／只读没有 Git 步骤 |
| 已中断 | Agent 进程退出时没有交付；保留进展，由用户决定重新安排或取消 |
| 待核对 | 租约过期或电脑失联，缺乏可靠证据；不等同于失败或完成 |

讨论、调查等只读任务不为交付而制造代码或提交。代码交付应提供实际基线、提交或未提交改动及验证情况，提交本身仍需项目规则和本次授权；平台保存引用，不保存源码，也不要求为填交付字段而越权提交。

## 6. 主要使用路径

### 从待办到执行

用户创建并整理任务，选「实现」（默认；既有任务也是实现）或「讨论」，明确项目和必要说明后安排开始。项目所在 Mac 的启动器在有空闲名额且条件满足时自动领取，在后台 tmux 会话中启动新的 Agent 会话并带上任务背景。

### 普通 Pi 发起并转后台

扩展只需向 Pi 登记一次本地 Steward 包。模型开始明确目标时自动登记，围绕同一目标的多轮对话沿用同一任务，普通随口问答不建任务。记录待办和登记正在执行的目标是不同操作。

前台目标交付收尾后，任务保留待验收状态，但普通 Pi 不退出，可以继续其他目标。切换尚未结束的目标须明确结束或中断原目标，不能把新要求悄悄写进旧任务。未配对或平台不可用时，新目标可以按本地授权执行，但必须说明尚未纳管；已纳管目标的历史记录不授予恢复后的执行权。

前台中断后，用户可在任务详情请求「后台继续」。原 Mac 的启动器必须在线、有后台名额，并可靠确认原 Pi 进程已退出；关闭页面、等待回复、断网和心跳超时都不是退出证据。接续保留同一任务、原对话、实际目录和分支；现场缺失、分支不匹配或主目录已有改动时停止并提示，不自动换电脑、换目录或搬运改动。任务列表和详情分别显示发起来源与当前执行方式，例如「用户前台发起 · 后台接续中」。

### 在任务中交流

Pi 通过 `steward_ask` 明确提出需要用户回应的问题后，等待满 3 分钟才在工作台显示一条提醒，同一次等待不重复。用户在原 Pi 会话回复，提醒自动撤下；打开会话不算回复，收到回复也不表示问题已经解决。问题是否解决仍由 Agent 根据交流内容更新。普通对话不触发提醒，也不把聊天同步到工作台。两种任务的后台执行共用本机后台名额，等待期间仍占用；普通前台执行不占后台名额。

Agent 把有意义的进展、重要决定与交付回报到任务。任务详情围绕目标与约定、当前进展、需要用户处理的事项、已有交付组织；Agent 的建议与用户已确认决定分别呈现。

### 从交付到验收

实现任务按目标执行并验证，完成后交付。讨论任务由用户在原 Pi 会话发送「结束讨论」，或在工作台点击「结束讨论」才收尾；已形成结论、不再继续发消息或当前回合结束都不自动收尾。工作台发起结束时，即使执行电脑离线也保留请求，恢复连接后由 Pi 保存简短结论和未决事项并收尾；正常交付和结算均保留正在运行的 Pi，专用任务 Pi 等到最终验收成功后才退出。结束讨论不等于取消或验收。

Agent 提交交付后，任务进入待验收；本轮实施、验证和必要回报全部收尾后明确结算，释放后台名额但保留 Pi。仅等待用户回复而尚未结算的后台工作仍占名额。用户在任务详情阅读结果、验证和验收方法，确认具体交付版本；旧版本的确认不能应用到新版本。

若只补最终报告、已有验证结果或遗留事项，在原 Pi 明确要求「仅补交付记录」。专用工具生成带来源和修订原因的新版本，保留旧版；不重新排队、不恢复实施权限，也不重复修改代码、发布或部署。若要求实质修改，须在原 Pi 明确授权续做，或在工作台正式返修，转换状态和权限后再实施。原 Pi 主动续做不受后台自动领取额度限制；打开或回复会话本身不完成转换。正式后台返修在原专用 Pi 仍运行时复用它，不另起第二份。

接入 Git 生命周期的代码任务，用户验收后进入待合并，不立即标记完成。平台安排操作，由仓库所在 Mac 的启动器程序将已验收的确切提交合回该任务记录的基准分支；同一仓库的操作串行，电脑离线则等待。最终合入只允许安全快进，避免程序在验收后生成未经确认的新文件树。基准已前进而不能快进、发生冲突或验证失败时，返回原任务现场，在任务分支同步、修复和验证，重新交付、重新验收。程序不替用户选择业务规则，Agent 不直接在基准分支修代码。

普通前台 Pi 在交付后仍可使用，不由任务台自动关闭。原前台进程尚未确认退出时，程序会暂停该任务的合并与清理，用户可退出原 Pi 后重试；不会因为尝试已经结算就删除可能仍在使用的逻辑工作树。

代码只有安全合并成功才算最终验收成功，合并失败仍须原现场修复、重新交付和重新确认。成功后封闭本任务的继续实施及交付修订权限，进入清理环境：确认专用任务 Pi 退出，再移除本任务专用工作树和任务分支。讨论、只读任务在人工验收成功后执行适用的退出清理。工作树有未提交改动、被占用、身份不符等情况时不强制清理，而是报告受阻；合并已经成功的重试只继续清理，不重复合并。项目原目录、基准分支、任务记录、交付和原生会话历史不删除。合并、清理及向远端推送、发布、部署分别核对；验收后的本地合并不授予后三者权限。

### 中断

用户可主动暂停进行中的任务。确认前会说明当前回复或工具可能中止，文件不回滚，已发出的外部操作可能已经生效。只有执行端确认 Pi 已停，才显示已暂停并释放其后台名额；处理中、离线、超时或结果未知都不冒称成功。

暂停后的「继续」在原电脑、原实际目录／工作树和原对话恢复。Pi 自动先核对最新任务、授权、实际进展和中断结果，再继续原授权内明确的步骤或提问等待，不重放旧命令。缺现场或会话、分支不符时停止，不创建替代现场。它与普通重启／恢复后等待用户消息不同，也不能通过「重新安排」绕过暂停接续。

非主动暂停的进程退出且当前工作段没有交付，仍记已中断，不自动重开；用户选择恢复、重新安排或取消。电脑失联显示待核对，不转给其他电脑。

### 自动续跑

启动器释放名额后继续领取用户已经安排、电脑匹配且没有未结束旧尝试的任务；返修优先。自动续跑不由模型猜测下一步工作。依赖调度与多 Mac 并用仍是候选；旧方案中的「默认等待前项验收」不是当前已启用的门禁，「上限三项」的验收积压门禁已按定位移出候选。

代码任务先明确项目默认或任务覆盖的基准分支。开工前同步默认开启，也可以关闭；开启时遵循该分支配置的上游，无上游则记录并跳过，有上游但同步失败不能冒充无上游继续。程序不强制重置分叉分支，也不覆盖项目原目录的改动。实际推进基准分支只对明确的 ref 做原子更新；若基准已在其他工作树中检出，程序暂停，由该目录所有者先切到其他分支，不在检查后再向他人的工作目录执行合并。

准备完成后固定实际基准分支和起点提交，再由项目 Agent 复用已有 Pi 工作树能力创建、迁移和登记独立任务分支与工作树；只读任务不创建工作树。开发和冲突修复均不直接在基准分支进行。首次领取时冻结整个基准分支和同步选择，未配置也保持未配置，不自动继承后来修改的项目默认。未选择分支的任务可由用户显式补选第一次分支，同时确认项目当前同步设置；此后目标锁定，准备完成后也不改变起点提交。返修先核对原现场，不能用新工作树替代缺失的原现场。跨任务依赖版本的联动属于后续设计，不静默改变现有任务基线。

## 7. 首版边界

- 面向个人在多个项目和多台 Mac 间使用；首版按一台 Mac 闭环验收，多机协调另行评估。执行端不支持 Windows／Linux，服务器操作系统另按部署环境确定。
- 平台在私人服务器以单 Docker 容器运行，利用已有 Docker Compose 与 HTTPS 环境。身份按个人使用简化，保留必要访问保护，不建设公开注册、团队权限或复杂设备审批体系。
- 当前只执行 Pi 任务；Claude Code 先作为讨论和建任务入口，作为执行端是后续方向，需要另行接入与验证。
- 后台任务只由启动器领取；普通 Pi 的明确目标可直接前台登记，不进入领取队列、不计后台名额。平台没有接收成功时不得声称已纳管。
- Agent 可代用户查看、创建和修改任务；安排开始与验收当前只能由用户在平台操作。按定位，用户在对话中明确授权后 Agent 可以代为安排开始，尚未实现；验收始终只由用户在工作台操作。
- 源码、Git 工作区、Agent 原生会话和模型凭据留在执行 Mac。
- 对话通过 Pi Reach 或本机终端进行，不在管家内嵌会话页面；精确会话深链仍是候选。前端已消费公开 PWA 基础包，但尚无 Service Worker 或 Web Push，工作台提醒不等于系统推送。
- 权限、提交、推送、合并及部署遵循各自项目规范和任务配置；管家不建立额外的工具审批体系。
- 平台根据用户操作、启动器报告的进程事实和项目 Agent 的明确回报更新状态，不以进程退出、退出码或模型一句自然语言回复推断验收通过。
- 电脑离线时仍可读取服务器已有的任务与交付资料；访问源码和运行本机预览需要对应电脑在线。
- 首版不做多用户团队协作、电脑远程唤醒或外部待办同步。
